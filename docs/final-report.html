Abstract

Modern enterprise computing increasingly relies on hybrid paradigms that combine low-level distributed infrastructure with high-level software-as-a-service platforms. This technical report comprehensively documents the architecture, implementation, and empirical verification of two complementary cloud practical projects:

  1. Project #9 — Private LAN SaaS Cloud Storage over Apache HDFS (Secure Cloud Vault): An end-to-end distributed storage system constructed using Python Flask and Apache Hadoop HDFS. Files uploaded via a web console are streamed, partitioned into fixed 2 MiB chunks, individually encrypted using authenticated symmetric cryptography (Fernet AES-128-CBC + HMAC-SHA256), and distributed into HDFS data blocks via WebHDFS. Retrieval is achieved by fetching encrypted blocks sequentially, authenticating and decrypting each segment in memory, and reassembling the exact bitstream for download without intermediate plaintext storage on disk.
  2. Project #8 — Custom Application on Salesforce Cloud Platform (Admissions Cloud Management): An enterprise-grade cloud CRM solution engineered on Salesforce Lightning Experience. It models the complete lifecycle of student recruitment and program enrollment using custom objects (Student_Inquiry__c), automated formula fields, validation rules, Lightning Path stage trackers, summary reports, and real-time executive management dashboards.

Both systems were developed, automated, and verified locally using WSL2 (Ubuntu 26.04 LTS) and Windows 11 host environments.

1. Introduction & Cloud Architecture Context

Cloud computing has revolutionized digital infrastructure by offering elastic, on-demand compute, storage, and application platforms. Within the National Institute of Standards and Technology (NIST) cloud framework, services are classified into three primary delivery tiers: - Infrastructure as a Service (IaaS): Provisioning fundamental compute, networking, and block/object storage abstractions (exemplified by HDFS nodes and raw Linux instances). - Platform as a Service (PaaS): Providing managed application runtime environments, database engines, and development frameworks (exemplified by Salesforce Force.com platform and Lightning App Builder). - Software as a Service (SaaS): Delivering fully managed, end-user applications hosted over network protocols without client-side management of lower tiers.

Project #9 demonstrates the bridge between IaaS and SaaS by building a secure, private cloud storage service on top of an underlying distributed cluster filesystem. Conversely, Project #8 explores enterprise multi-tenant PaaS by configuring and automating domain-specific business processes on Salesforce.

2. Project #9: Private LAN SaaS Cloud Storage over HDFS

2.1 Problem Statement & Scope

Standard Network Attached Storage (NAS) and traditional web file managers suffer from three key deficiencies in untrusted or distributed environments: 1. Single Points of Failure & Inflexible Scaling: Monolithic disks do not scale horizontally across physical drives or network nodes. 2. Plaintext Vulnerability at Rest: Files stored directly on storage nodes are susceptible to unauthorized physical or administrative inspection. 3. Bandwidth Inefficiencies with Large Files: Transmitting monolithic files as single streams creates memory bottlenecks and lacks fault tolerance during network interruptions.

Project #9 addresses these challenges by developing a zero-trust, chunk-partitioned SaaS storage layer hosted on a local area network (LAN) backed by Apache Hadoop Distributed File System (HDFS).

2.2 System Architecture & Data Flow

The architecture operates on a decoupled multi-tier topology: 1. Client Tier: Web browser accessing the modern glassmorphism UI via HTTP port 5000. 2. Application Tier (Flask Controller): Acts as the storage gateway, performing cryptographic key management, streaming file ingestion, chunk boundary division, and metadata persistence. 3. Cluster Storage Tier (Apache Hadoop HDFS): - NameNode (Daemon): Listens on TCP port 9000 (RPC) and HTTP port 9870 (WebHDFS), maintaining namespace metadata and chunk directory mapping. - DataNode (Daemon): Listens on TCP port 9866 (data streaming) and HTTP port 9864 (WebHDFS chunk transfer), writing and replicating blocks to underlying storage. - Secondary NameNode: Consolidates fsimage snapshots and transactional edits logs.

2.3 Cryptographic Security Model

To enforce zero-knowledge at rest across the distributed filesystem, encryption occurs before data is dispatched to HDFS. The application leverages Fernet symmetric cryptography from the Python cryptography library:

  • Algorithm: Advanced Encryption Standard (AES) in Cipher Block Chaining (CBC) mode with a 128-bit key.
  • Integrity & Authentication: Hash-based Message Authentication Code (HMAC) utilizing SHA-256 with an independent 128-bit key (256-bit combined key material).
  • Initialization Vector (IV): A cryptographically strong, random 128-bit IV generated per chunk via os.urandom().
  • Padding: PKCS7 padding to align arbitrarily sized chunks with AES 128-bit block boundaries.
  • Key Isolation: The master key is stored in saas_cloud/secret.key with strict permissions and excluded from Git commits via .gitignore. Even an adversary with direct root access to the HDFS DataNode filesystem can inspect only high-entropy encrypted ciphertext blocks.

2.4 2 MiB Partitioning & WebHDFS Distribution Pipeline

When an applicant or administrator uploads a payload: 1. Streaming Buffer: The controller reads the incoming stream in increments of CHUNK_SIZE = 2,097,152 bytes (2 MiB). 2. Chunk Processing: $$\text{Total Chunks } N = \left\lceil \frac{\text{File Size}}{\text{CHUNK_SIZE}} \right\rceil$$ 3. Ciphertext Output: $$\text{Encrypted Chunk} = \text{FernetEncrypt}_{K}(\text{Chunk}_i)$$ 4. HDFS Ingestion: The controller issues an HTTP PUT to: http PUT /webhdfs/v1/saas_cloud/{file_id}/chunk_{i}.enc?op=CREATE&overwrite=true The NameNode redirects (HTTP 307) the upload to the active DataNode (http://localhost:9864), which writes the encrypted block to disk. 5. Metadata Registration: The controller records an entry in files.json: - file_id: Unique UUIDv4 identifier. - filename: Sanitized original name via werkzeug.utils.secure_filename. - size: Exact unencrypted byte count. - chunk_count: $N$. - chunks: List of objects specifying chunk indices, raw bytes, encrypted byte size, and HDFS URIs. 6. Reassembly on Download: - Chunks are fetched sequentially from index $0$ to $N-1$ over WebHDFS. - Each ciphertext is validated and decrypted into memory. - Decrypted bytes are written sequentially into an in-memory io.BytesIO stream. - The verified stream is delivered via HTTP Content-Disposition: attachment.

3. Project #8: Custom Admissions Application on Salesforce Cloud Platform

3.1 Problem Statement & Educational Domain Overview

Higher education admissions offices receive thousands of prospective inquiries annually across diverse academic programs. Traditional manual spreadsheets and disconnected email chains create critical operational bottlenecks: 1. Unorganized Lead Tracking: Difficulty in identifying which leads have been contacted versus those awaiting scheduled counseling. 2. Manual Evaluation Overhead: Counselors manually compute qualification thresholds for merit-based scholarships. 3. Zero Leadership Visibility: Executive admissions deans lack real-time visibility into conversion bottlenecks and intake capacity.

Project #8 resolves these issues by engineering a custom cloud application on the Salesforce Lightning Platform called Admissions Cloud Management.

3.3 Lightning App Architecture & Dynamic Path Assistant

The application is deployed as a Lightning App (Admissions_Cloud_Management) incorporating: - Consolidated Navigation Bar: Home, Student Inquiries, Reports, and Dashboards. - Dynamic Lightning Path: A visual chevron progress tracker positioned on top of the record page bound to Inquiry_Status__c. Counselors advance inquiries with a single click across the pipeline: $$\text{New} \longrightarrow \text{Contacted} \longrightarrow \text{Counseling Scheduled} \longrightarrow \text{Application Submitted} \longrightarrow \text{Enrolled}$$ - Highlights Panel: Surfaces high-priority fields at a glance (Status pill, Program, GPA percentage, and dynamic Scholarship eligibility checkmark).

3.4 Business Logic, Automation & Validation Rules

To preserve data integrity, declarative validation rules were implemented: 1. VR01 — GPA Bounds Checking (VR_GPA_Percentage_Range): sql OR(High_School_GPA__c < 0.0, High_School_GPA__c > 1.0) Prevents counselors from entering out-of-range academic percentages. 2. VR02 — Mandatory Contact Channel (VR_Email_Or_Phone_Required): sql AND(ISBLANK(Email__c), ISBLANK(Phone__c)) Guarantees that an applicant cannot be saved without at least one actionable contact channel. 3. Automated Merit Evaluation: The formula field Scholarship_Eligible__c executes instant client-side and server-side evaluation upon saving or modifying academic GPA, eliminating human miscalculation.

3.5 Analytical Reports & Executive Decision Dashboard

Business intelligence is delivered via two custom reports and an executive dashboard: - Pipeline Summary Report: Groups all 12 student inquiry records by Inquiry_Status__c and summarizes academic credentials across each degree program. - Scholarship Candidate Report: Filters records where Scholarship_Eligible__c = TRUE (7 out of 12 sample applicants qualifying). - Executive Admissions Dashboard: 1. Funnel Component: Tracks the lead-to-enrollment attrition rate. 2. Program Demand Donut Chart: Visualizes application volume by degree (B.Tech CS and AI/Data Science leading demand at 25% each). 3. Enrollment Target Gauge: Displays real-time progress toward the 10-student cohort target (currently 30% achieved). 4. Scholarship Rate Metric Card: Displays the 58.3% merit qualification rate.

6. Engineering Challenges, Troubleshooting & Gotchas

During the implementation of both cloud projects, three critical engineering hurdles were diagnosed and resolved:

1. WSL2 Systemd Daemon Lifecycle Management

  • Symptom: When start-dfs.sh was executed directly in transient WSL sessions, the NameNode and DataNode daemons shut down after a brief window with signal SIGHUP / SIGTERM.
  • Root Cause: WSL2 automatically reclaims child process groups when transient non-interactive terminal sessions terminate.
  • Resolution: Implemented a native systemd unit service (/etc/systemd/system/hadoop-hdfs.service) with Type=oneshot and RemainAfterExit=yes. This enabled persistent daemon operation across background sessions and automatic startup upon VM invocation.

2. WebHDFS 307 Redirect & Cross-Platform Hostname Resolution

  • Symptom: Windows applications querying WebHDFS NameNode (http://localhost:9870/webhdfs/v1/...) threw NameResolutionError: Failed to resolve 'laptop-mlc7cll4.localdomain'.
  • Root Cause: During write operations, the HDFS NameNode returns an HTTP 307 redirect instructing the client to contact the DataNode by its canonical Linux hostname (laptop-mlc7cll4.localdomain). While resolvable inside Ubuntu, the Windows DNS resolver does not resolve internal WSL localdomain addresses.
  • Resolution: Updated hdfs-site.xml with: xml <property> <name>dfs.datanode.hostname</name> <value>localhost</value> </property> This enforced that WebHDFS returns http://localhost:9864 on redirects, making the endpoint universally routable across both Windows host scripts and internal WSL processes.

3. Zero-Knowledge In-Memory Reassembly

  • Symptom: Large file downloads risked exhausting local disk space or leaking temporary unencrypted files.
  • Resolution: The download controller was architected to stream encrypted chunks directly into memory, decrypt each sequentially via Fernet, and stream directly into Flask's send_file using an in-memory buffer (io.BytesIO), leaving no unencrypted residue on disk.
